# Phase 34, lane b7: defects the widget docs lane found

## What changed
- **Rows cross the frame as plain data** (`packages/widget-sdk/src/frame.ts`): `toWireData` makes a rows input's `more`/`sortBy` the flags `hasMore`/`canSort`; `fromWireData` makes the functions again in the frame (`packages/widget-frame/src/index.ts`), each posting a new frame message, `more {input}` or `sort {input, sort|null}` (`isFrameMessage` knows both). The host (`packages/screens/src/TenantWidgetHost.tsx`) posts only wire data, and answers a request by calling the page's real `more()` / `sortBy()` (the sort column must be one the rows have). `frameChannel.ts` validates them like events: only for a rows input the definition declares (`createChannel({rows})`, `Object.hasOwn`-style set), at most `FRAME_LIMITS.requestsPerSecond` = 4 a second.
- **A post that fails is not swallowed**: the cell says "This widget could not be given its data" (role alert, over the kept frame) and the console logs why.
- **Real state**: `WidgetViewProps.state` (optional); `PageView.tsx` passes the page's read state for `x/` widgets; `Frame.tsx` keeps a tenant widget mounted in loading, empty, failed, forbidden (it adds a **Try again** button under failed/forbidden), where core widgets get the platform's notice. The host posts it.
- **Generator** (`packages/docs/generators/dts.mjs`): a type's `<...>` arguments no longer split at their comma, so `parent?: Pick<Window, "postMessage">` is whole.
- **Docs**: security page and four fact-check records re-checked against merged b4r code (frame-src `app.ts:426`, `patternProblem` ReDoS limits, `Object.hasOwn`, content type from the file name, `WIDGET_POLICY` on every `/_widgets/` answer) and updated; rows limit, state and the failed post described in `what-a-view-is-given`, `the-widget-frame`, `writing-a-widget`.
