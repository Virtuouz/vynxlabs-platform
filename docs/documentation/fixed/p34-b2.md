# Phase 34, lane b2: build, deploy and pin a developer's widget

## What changed
- Build: `packages/cli/src/widget-build.ts` (new) bundles each widget's `entry` with esbuild (iife, browser, minified, React and `@volvel/widget-frame` inside) into `view-<sha8>.js`, plus `frame.html`. Refused, with the widget named: a module from `http(s)://`, any `import()` (a plugin refuses it; a scan of the output catches a computed one), a script over 512 KB (the message gives its size), a view that does not build (file:line and esbuild's text). `build.ts:324` carries both files as assets with `app` = the widget's type, hashed and uploaded like an app's; a bundle with a widget is format 2+.
- Bundle check: `packages/manifest/src/bundle-check.ts` `checkBundleAssets`: an asset's owner may be a widget; a widget has exactly `frame.html` and one `view-<8 hex>.js`. `WIDGET_FRAME_FILE` and `WIDGET_POLICY` exported. `docs/contracts/bundle.md` says so.
- Storage: migration `packages/db/migrations/0101_widget_version.sql` (locked), table `widget_version` (workspace, type, version, definition, files, files_digest, bundle), listed in `tenancy/tables.ts`. `kernel/widgets.ts`: `storeWidgetVersions` (deploy.ts, first thing), refuses other files for a stored version in any workspace of the tenant (`widget_version_changed`); several versions stay. `sweepAppFiles` (`apps/assets.ts`) keeps the files a version names.
- Pinning (EXT-20): `PageWidget.version` (`widget-sdk/src/page.ts`, `pageWidgetSchema`), schemas re-emitted. `versionProblems` is in `interfaceProblems`, `dashboardProblems`, `unknownTables` (drafts: said, saved) and in `deployBundle` (`widget_version_missing`, 409). An `x/` widget with no version is a problem too.
- Removal: `refuseWidgetInUse` (`widget_in_use`, names each page, member dashboards too): in `deployBundle` for a widget the bundle drops, and in `DELETE /tenants/:t/workspaces/:w/widgets/:name/versions/:version` (needs `deployment:write`; also refused for the version the repository defines now).
- Data for the inspector: `GET /tenants/:t/workspaces/:w/widgets` (`routes/widgets.ts`): `{items: [{type, current, versions: [{version, current, deployedAt, files, bytes, placements, definition}]}]}`, oldest first; `resource:read`, `interface:read` or `dashboard:read`.
- Serving: `front.ts` `serveWidgetFile`: `GET /_widgets/<tenant slug>/x/<name>@<version>/<file>` at the apps address, a registered hostname (that tenant's only), or the console address when apps run there (`runsCodeApps`); the instance address with a second apps address redirects (307) as apps do. Content policy `WIDGET_POLICY`, `immutable` caching, `nosniff`, no-referrer; reads and sets no cookie; rate-limited like app files.

## Contract changes other lanes must know
- b3: a bundle that places `x/goal` passes the checker only once the workspace's widgets are registered (`registerWidgets`); my tests register by hand. Place a widget with `version` set to the current version; the server refuses `x/` widgets without one. "Update to vN": read versions from the GET above and write `version` on the instance.
- b4: frame URL is `<appsOrigin>/_widgets/<tenant slug>/x/<name>@<version>/frame.html`; the files are public (no cookie, no session), same for every viewer.
- Integrator: the migration is `0101` here because versions must be consecutive in this worktree; a2 also has 0101. Renumber to 0102 and run `node scripts/migrations-lock.mjs --update`. Several workspaces of a tenant share one address per type@version, so the same version must have the same files everywhere; a dev workspace that changes a view without raising the version is refused.
