# Historical polish analysis

Status: analysis only. Written 2026-11-20 against `phase-21-docs-redesign` at `f54d4bc` (316 commits, 2026-11-11 to 2026-11-20; the history is not shallow).

This document asks what had to be corrected after a phase or milestone was called built, and why. The evidence is the git history (diffs read, not only messages) and the phase documents' Findings, "after the owner's first look" and walk-through sections. The full evidence table is in the [appendix](#appendix-evidence-tables). The rules drawn from it are in [polish-prevention-rules.md](polish-prevention-rules.md).

## How the history was read

- **Milestones** are the phase documents' milestones (`docs/phases/phase-N-*.md`) and the commits titled `Phase N: …`. Phases 12 to 16 carry out a planned audit (`docs/uiux/09-prioritized-uiux-roadmap.md`), so their audit items are **planned polish** and are counted apart from reactive corrections.
- **A correction** is a change to work that had already been committed, or that a phase document says was found after the first version, where the first version fell short for a person using it. New scope, refactoring, test or CI maintenance and backend defects without a user-facing shortfall are listed but not counted.
- **Pairing.** Each correction was paired with the commit that introduced the shortfall, by `git log -S`, `git log --follow` on the files it touched, and the phase documents' own references. Where the original could not be pinned, the row says so.
- **Who found it.** "Owner-requested" is set only where a phase document says the owner found or asked for it. No motive is inferred beyond the documents and diffs.
- **Checking.** The work was split by phase range (0–11, 12–17, 18–21), and each range was read separately. 26 of the cited commits, about a fifth, were then checked again for date, subject and the hunk the claim depends on, for example the `uuid` filter removed in `512faf1`, `data-closed` in `8748202` and the Grid's `stopPropagation` in `60695d2`. All 26 matched.

### Representative before and after

**1. States.**
- A trigger run by hand still said "Last fired: Never". It now says "Not fired yet. Runs started by hand are not counted." (`010305b`, H0-34)
- A failed run's attempt read "#1 succeeded". The last attempt of a failed run is now failed (`560e9d3`, H12-34)

**2. Equivalent things.**
- There were three run-state maps, and "Waiting" meant queued in one and approval in another. Now there is one server-derived state (`d1ec682`, H0-53)
- The flow editor and the app builder had undo and redo. The dashboard builder had undo for layout only, until the owner asked (`afebae1`, H18-22, `docs/phases/phase-19-dashboards-motion.md:170`)

**3. Lifecycle.**
- The console could only make and delete groups, "though the API could do the rest" (`9b433c2`, H0-20)
- Moving a docs page meant typing its path, until dragging was added "at the owner's word" (`2542b42`, H18-27)

**4. Layout.**
- Rows behind a number appeared in a 30rem dialog around a 60vh table. It is now a table-sized dialog with sort, filter and columns (`9288278`, H18-13)
- The runs list had two scroll bars. It now has one (`07c5d38`, H18-02)

**5. Phone.**
- The docs navigation covered the page on a phone. Found in the first browser run, an hour after the milestone (`60695d2`, H18-23)
- An account key's "Last used" was 4 px too wide at 390 px (`3e72be9`, H12-44)

**6. Keyboard.**
- A column's ⓘ stopped every key, so F1 and ⌘K did nothing on a table screen (`32f9d13` → `60695d2`, H18-24)
- Esc did nothing while a just-closed menu faded out (`8748202`, H18-21)

**7. Navigation.**
- The failed-runs chip opened an unfiltered list (`3a4cf6e`, H0-44)
- Inside a dashboard the breadcrumb could not lead back (`543706b`, H18-16)

**8. Copy.**
- "Started … by by hand" (`bfb7942`, H0-02)
- "Cannot be changed later" stayed after renames were built (`ed2c0b3`, H12-46)

**9. Fix in one place.**
- Phase 7 stopped short fields being drawn as boxes at one call site (`73ae1b5`). Phase 9's shared SchemaForm brought it back, and phase 10 fixed it a second time (`934baca`). H0-26 → H0-64.
- Phase 18 gave the docked drawer motion, and phase 19 found the narrow sheet beside it had none (`07c5d38` → `72628e7`, H18-10).

**10. Schema forms.** An enum without `type` was dropped from the mail connection form (`73ae1b5`, H0-25).

**11. Latency.** A dragged widget snapped back, then moved again, while its save was in flight. It is now drawn at once, with saves queued (`8748202`, H18-20).

**13. Motion.** About fifteen sheets and dialogs appeared and vanished in a frame (`72628e7`, H18-09). The served docs site then had none either (`f54d4bc`, H18-34).

## Why these survive to the owner (hypotheses)

Each hypothesis is followed by the evidence for it and how strong that evidence is.

1. **Milestones are done when their capability works, not when their journey does.**
   - Exit criteria in the phase documents name capabilities. Phase 21's are "a page four folders deep is served", "a folder is made, renamed, moved and deleted" (`docs/phases/phase-21-docs-redesign.md:7-13`).
   - The lifecycle, state and sibling gaps (patterns 1, 2, 3) are exactly what such criteria leave out.
   - Strength: strong.
2. **Browser walks happen after "built", or not at all.**
   - Phase 20 M8 and M9 were "not seen in a browser" (`docs/phases/phase-20-documentation.md:413,452`). Two defects appeared within an hour of the first browser run.
   - Phase 21's walk-through "was not run" (`docs/phases/phase-21-docs-redesign.md:59`), and the owner's first look followed.
   - About 60 of the 124 items were found only in a browser or on an instance.
   - Strength: strong.
3. **Unit tests render in happy-dom without the shell.**
   - Phase 12 records an error boundary "not in the unit test, which renders the screen without the shell" (H12-01).
   - Phase 13 records virtual rows "measured as they draw" (H12-10).
   - Layout, motion, focus and latency cannot fail there.
   - Strength: strong for patterns 4, 5, 6, 11 and 13.
4. **Guards are written per surface, and new surfaces start without them.**
   - The motion, list, header and table rules live in `apps/console/src/enforce.test.ts`.
   - The served docs site (`apps/control-plane/src/kernel/apps/docs.ts`, `packages/markup/src/enhance.ts`) is outside them, and repeated the motion shortfall in phase 21 (H18-34).
   - The `e2e/polish.spec.ts` measures cover the workbenches they list.
   - Strength: strong for pattern 13, medium otherwise.
5. **Fixes go where the symptom is.**
   - `maxLength` (H0-26 → H0-64), the drawer's two forms (H18-01 → H18-10), and the guards above.
   - Strength: medium. Three clear cases.
6. **New screens copy a sibling instead of sharing it.**
   - Three status maps (H0-53), two column menus (H18-05), two renderers of a docs page (H18-35), and differing validators (H0-40).
   - Strength: strong.
7. **Copy is not revisited when a capability changes.**
   - "Cannot be changed later" (H12-46), the CLI-only empty state (H0-49), and the tenant plan's warnings never built (H12-41).
   - Strength: medium.
8. **Scope trimmed while building is reported at the bottom of the milestone, not raised.**
   - Phase 20's "Not built" lists (`docs/phases/phase-20-documentation.md:450`) became the owner's asks within hours (H18-25 to -28).
   - Strength: medium.

There was no evidence for a missing design specification as a cause. Phase 19 and 21 worked from the owner's own mock-ups, and the shortfalls were in behaviour that the mock-ups do not show: motion, states, phone, keyboard and lifecycle.

## Limits

- **Single author.** Every commit is by one author, through an agent. "Owner-found" rests on the phase documents' own words.
- **Intra-commit corrections.** Phases 9, 10 and from 12 onwards often fixed a walk's findings inside the milestone commit, so the first version is not in the history. Those 10 rows rely on the documents alone.
- **Uncertain rows are not in the counts.** The 34 uncertain rows (backend defects, mixed motives, test determinism) are excluded. Including them would raise patterns 1, 3 and 11.
- **The window is nine days long.** The days-to-fix figures are in fractions of a day and reflect the pace of agent-built phases. They are not comparable with a team's cycle times.
- **Phases 0 and 1 have no corrections.** They built the kernel, which had no console screens to correct.

#### Method and caveats

- I read every phase doc's Findings, Verification, Known gaps and Owner decisions sections for phases 0 to 11, the Fernhill README as it was at `abb4d73`, and 04-ux-audit.
- I picked out commits whose messages show correction ("found", "fixes from verification", "walk", "no longer", "used to", "wrongly", "could only"), and grepped every commit body in the window for those cues. I checked the console and kit diffs with `git show <hash> -- <file>`. The diffs I read are cited in the Evidence column.
- **Days** is the gap between commit dates (calendar days, author dates). Many follow-ups land minutes after the original: phases 5 to 8 were each built and verified within hours.
- **Intra-commit** means the doc says a walk or test found the problem before the milestone's single commit was made, so the first version is not in history. Phase 9 and 10 use one commit per milestone. These rows count as evidence of first-implementation shortfalls, but no "before" diff exists.
- **Classification:** "corrective polish" means a user-facing shortfall in behaviour, state, copy, layout or a11y in already-shipped work. "Enhancement" means new capability. "Uncertain" covers planned redesign scope that also removed earlier shortcomings, cases where the motivation isn't stated, and backend defect fixes that are corrective but are not UI polish. Those are marked "(defect)".
- **Owner-requested** is "yes" only when a doc says so. Otherwise it is "not stated". No correction in this window is described as raised by the owner from using the product. The owner approved scopes that contained corrections (phase 6 scope, phase 9 = audit P0/P1, phase 11 dev-workspace pause). Those cases are marked.
- Phases 0 and 1 have no corrective commits. `86307e5` only records a Postgres test result in the doc.
