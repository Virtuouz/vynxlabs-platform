# Phase 34, A9: a pull brings a resource taken over in the console

Fixes the data-loss bug of `p34-a7r.md`: after a table was taken over in the console, `volvel pull` wrote nothing, recorded the basis, and the next deploy retired the console's column.

## What changed
- `apps/control-plane/src/kernel/authoring.ts` `activeConsoleManaged` reads the resource rows (ownership `ui`), not the active bundle. `resource-files` (`routes/authoring.ts`) and its `basis` now come from the same rows, so a taken-over table is written as `<path>.table.yaml`. Git sync uses the same function and now sees such resources too.
- `packages/cli/src/pull.ts`: the basis is sent only for resources whose file the pull wrote or already found identical; for a resource still defined in code it prints where (by name when the file is unknown) and that a deploy is refused as defined twice. `resource-files` returns `inCode` (`routes/authoring.ts`), from the new `ResourceMeta.inCode` (`packages/db/src/schema.ts`), set by `putResource` (`kernel/resources.ts`, `takenOver`) when a table is taken over (`routes/workspaces.ts`) or a draft deploy takes a resource over (`kernel/execution/deploy.ts`), kept by later console deploys, cleared by a deploy of the repository.
- Second hole found while running the bug: the basis of a table taken over was its state after the same save, so a column added in that save was not protected. It is now the hash of what the code had (`routes/workspaces.ts`). A draft deploy that takes a code resource over (a flow) set no basis, so a deploy of the code took it back silently; it now sets the code's hash (`deploy.ts`). Both are refused with `console_changed`, overridable by `--force`. The test of the draft take-over in `authoring.test.ts` now expects that refusal, then forces.
- Dialog and notices: `kit/ownership.ts` (`takeOverConsequence`, `takesItBack`), `screens/Data.tsx`.
- Five pages and their fact-check records.
