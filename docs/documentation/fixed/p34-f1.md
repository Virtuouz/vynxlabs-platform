# Phase 34, lane f1: focus at 390 px in a confirmation dialog

Lane e1 recorded that at 390 px, two Tab presses from Cancel in the confirmation a frame's write event opens left the focus outside the dialog.

## Result: not reproduced as an escape; no product code changed

Instance on port 4369 (database f134), the fixture tenant of `e2e/widget-frame.spec.ts` (a sandboxed frame behind the dialog). At 390, 768 and 1440 px, Tab 8 times then Shift+Tab 8 times, `document.activeElement` read after each press.

- Read at once after the press, all three widths show `OUT` samples: the `<span>` focus guards Base UI puts at each end of the popup (at 390 also `BODY`), and the frame's `IFRAME` after Shift+Tab from Close. The wider widths show them too, so e1's "only at 390" was a sampling difference.
- Read after 150 ms, every sample at every width is a button in the dialog (Cancel, Confirm, Close), cycling both ways. Also with `isMobile` and touch at 390, light and dark, and after a reload: always inside.
- So the guards (and the frame, before the guard's handler moves the focus on) hold the focus for an instant; it settles inside. Nothing keeps it outside. A key typed in that instant could reach the frame; not observed.

Not checked: other modal pieces (SideSheet, palette sizes) were not run, since the shared Dialog showed no fault; they use the same Base UI popup.

## Test

`e2e/widget-frame.spec.ts`, last test, at 390, 768, 1440: after every Tab and Shift+Tab (8 each) the focus settles inside the dialog (`expect.poll`). 12 passed in the spec.

## Left

If a person still sees a stuck focus at 390 on a real phone, it needs a device; a desktop emulation shows none.
